# Выпуск физической карты новым пользователем (gRPC)

Сценарий `IssuePhysicalCardSequentialTaskSet` (наследник `GatewayGRPCSequentialTaskSet`):
создание пользователя → открытие дебетового счёта → выпуск физической карты.
Все вызовы идут через grpc-gateway (`localhost:9003`) gRPC API клиентами из `clients/grpc/gateway`.
Виртуальный пользователь — `IssuePhysicalCardScenarioUser` (наследник `LocustBaseUser`).

Запуск из корня проекта:

```bash
locust --config=./scenarios/grpc/gateway/new_user_issue_physical_card/v1.0.conf
```

## Профиль нагрузки

`users = 30`, `spawn-rate = 3`, `run-time = 3m`, headless.

- Флоу популярный, но не пиковый: новые пользователи приходят постоянно, но без массового наплыва.
  Нужна умеренная рабочая нагрузка, а не стресс.
- Стенд целиком работает на машине с 2 vCPU, генератор нагрузки — на ней же. Узкое место флоу —
  асинхронная часть: на каждый открытый счёт консьюмер kafka-documents формирует документы (договор и тариф)
  и кладёт их в MinIO. На пробном прогоне с 50 пользователями задержки gRPC ещё приемлемые (p95 ≈ 270 мс),
  но kafka-documents уже не успевает: отставание обработки событий росло весь прогон (до ~80 с),
  после остановки он дорабатывал ещё около 410 договоров и столько же тарифов. При 30 пользователях
  отставание выросло до ~48 с к 10:09:40 и дальше не росло; после окончания теста kafka-documents
  дорабатывал около 220 договоров и 230 тарифов (до 10:11:18). CPU всех контейнеров ≈ 130 % из 200 %.
- Это тот же профиль, что и у HTTP-версии сценария (`scenarios/http/gateway/new_user_issue_physical_card`),
  поэтому результаты можно сравнивать напрямую.
- `spawn-rate = 3`: все 30 пользователей стартуют плавно, примерно за 10 секунд.

Весов у задач нет: в `SequentialTaskSet` шаги выполняются строго по очереди, по одному разу за итерацию.
В отчёте каждая задача занимает 33,3 %. Каждая итерация создаёт нового пользователя, за прогон их создано 861.

## Сравнение с HTTP-версией

Оба сценария запускались с одинаковым профилем: 30 пользователей, 3 минуты.

| Показатель | HTTP | gRPC |
|---|---|---|
| Запросов / Fails | 2382 / 0 | 2561 / 0 |
| RPS | 13,2 | 14,2 |
| Aggregated p50 / p95 / p99, мс | 130 / 580 / 1100 | 44 / 180 / 270 |
| p95 открытия счёта, мс | 730 | 230 |
| CPU шлюза | http-gateway ≈ 51 % | grpc-gateway ≈ 13 % |

RPS почти одинаковый: его задают число пользователей и пауза 1–3 секунды между задачами.
gRPC отвечает примерно в 3 раза быстрее по p95, а шлюз тратит примерно в 4 раза меньше CPU.
