# Выпуск виртуальной карты существующим пользователем (gRPC)

Сценарий `IssueVirtualCardTaskSet` (наследник `GatewayGRPCTaskSet`): существующий пользователь получает список
своих счетов и выпускает новую виртуальную карту. Все вызовы идут через grpc-gateway (`localhost:9003`)
gRPC API клиентами из `clients/grpc/gateway`. Виртуальный пользователь — `IssueVirtualCardScenarioUser`
(наследник `LocustBaseUser`).

Запуск из корня проекта:

```bash
locust --config=./scenarios/grpc/gateway/existing_user_issue_virtual_card/v1.0.conf
```

Хук `events.init` перед стартом нагрузки выполняет сидинг `ExistingUserIssueVirtualCardSeedsScenario`:
300 пользователей, у каждого дебетовый счёт. Сидинг идёт через gRPC и занимает около 30 секунд.
В `on_start` после `super().on_start()` каждый виртуальный пользователь берёт случайного пользователя из сидинга:
`get_random_user()` сохраняется в `self.seed_user`.

## Веса задач

| Задача | Вес | Почему |
|---|---|---|
| get_accounts | 3 | с него начинается работа с приложением; после выпуска карты пользователь снова запрашивает список счетов, чтобы увидеть новую карту (карты приходят в ответе на список счетов) |
| issue_virtual_card | 1 | выпуск карты — редкое действие, поэтому у него минимальный вес |

В отчёте фактическое распределение запросов 75,7 % / 24,3 %, что соответствует весам 3 : 1.

## Профиль нагрузки

`users = 60`, `spawn-rate = 4`, `run-time = 3m`, headless.

- Флоу частый и критичный, но карты выпускают реже, чем смотрят операции. Поэтому пользователей здесь меньше,
  чем в сценарии получения операций (100), и больше, чем в сценарии нового пользователя (30).
- Стенд целиком работает на машине с 2 vCPU, генератор нагрузки — на ней же. Сидинг открывает 300 дебетовых
  счетов, и первые 1,5–2 минуты kafka-documents формирует по ним документы, занимая до 70 % ядра.
  Пробные прогоны по 2 минуты:
  - 80 пользователей — в первую минуту, пока kafka-documents разбирает очередь, p95 доходит до 1–2 с,
    итоговый p95 ≈ 890 мс;
  - 60 пользователей — всплеска нет, p95 ≈ 78 мс, CPU машины ≈ 133 % из 200 %.
- `spawn-rate = 4`: пользователи стартуют плавно, примерно за 15 секунд.
- Каждый виртуальный пользователь берёт случайного пользователя из 300 подготовленных, выбор идёт с повторами.
  По логам grpc-accounts в этом прогоне список счетов запрашивали 55 разных пользователей из сидинга,
  остальные 245 в тесте не участвовали.

## Результаты (report.html)

Прогон: 01.10.2026 10:41:08–10:44:08 UTC, сидинг перед ним — с 10:40:38. В report.html время показывается
в часовом поясе браузера, на скриншотах Grafana — в UTC.

Полные имена методов начинаются с `/contracts.services.gateway.`.

| Метод | Запросов | Fails | p50, мс | p95, мс | p99, мс |
|---|---|---|---|---|---|
| accounts.AccountsGatewayService/GetAccounts | 3865 | 0 | 30 | 84 | 140 |
| cards.CardsGatewayService/IssueVirtualCard | 1238 | 0 | 33 | 86 | 120 |
| **Aggregated** | **5103** | **0** | 31 | 85 | 130 |

- Fails = 0, RPS в среднем ≈ 28,3.
- Выпуск карты немного медленнее списка счетов (медиана 33 мс против 30 мс): это запись новой карты, а не чтение.
- На графике Response Times в отчёте p95 поднимается до 220–270 мс только в первые 25 секунд, пока стартуют
  пользователи, а kafka-documents разбирает очередь после сидинга. Дальше p95 держится на 50–110 мс.
- Задача выпуска карты в TaskSet повторяется — это осознанное ограничение модели: она задаёт интенсивность
  вызовов IssueVirtualCard на систему. Выпущенные карты приходят в ответе на список счетов, поэтому этот ответ
  постепенно растёт (в среднем 2,0 КБ) — отсюда рост сетевого трафика на скриншоте при постоянном RPS.

## Сравнение с HTTP-версией

HTTP-версия сценария (`scenarios/http/gateway/existing_user_issue_virtual_card`) запускалась с 50 пользователями,
веса задач те же.

| Показатель | HTTP, 50 пользователей | gRPC, 60 пользователей |
|---|---|---|
| Запросов / Fails | 4053 / 0 | 5103 / 0 |
| RPS | 22,5 | 28,3 |
| Aggregated p50 / p95 / p99, мс | 74 / 220 / 1100 | 31 / 85 / 130 |
| Средний ответ со списком счетов | 3,9 КБ | 2,0 КБ |
| CPU шлюза | http-gateway ≈ 69 % | grpc-gateway ≈ 13 % |

gRPC обслуживает больше пользователей с задержками в 2–3 раза ниже. Карт на пользователя к концу обоих прогонов
набирается сопоставимо, а ответ со списком счетов в protobuf примерно вдвое меньше, чем в JSON. Шлюз тратит
на один запрос примерно в 6–7 раз меньше CPU.
