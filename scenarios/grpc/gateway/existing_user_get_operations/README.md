# Получение операций существующим пользователем (gRPC)

Сценарий `GetOperationsTaskSet` (наследник `GatewayGRPCTaskSet`): существующий пользователь получает список
счетов, список операций и статистику по операциям. Все вызовы идут через grpc-gateway (`localhost:9003`)
gRPC API клиентами из `clients/grpc/gateway`. Виртуальный пользователь — `GetOperationsScenarioUser`
(наследник `LocustBaseUser`).

Запуск из корня проекта:

```bash
locust --config=./scenarios/grpc/gateway/existing_user_get_operations/v1.0.conf
```

Хук `events.init` перед стартом нагрузки выполняет сидинг `ExistingUserGetOperationsSeedsScenario`:
300 пользователей, у каждого кредитный счёт и 7 операций (5 покупок, пополнение, снятие наличных).
Сидинг идёт через gRPC и занимает около 1 минуты 45 секунд.
В `on_start` после `super().on_start()` каждый виртуальный пользователь берёт случайного пользователя из сидинга:
`get_random_user()` сохраняется в `self.seed_user`.

## Веса задач

| Задача | Вес | Почему |
|---|---|---|
| get_accounts | 1 | список счетов открывают при входе, чтобы проверить баланс |
| get_operations | 3 | историю операций обновляют чаще всего, чтобы убедиться, что платёж прошёл |
| get_operations_summary | 2 | статистику открывают реже, чем историю, но тоже неоднократно |

В отчёте фактическое распределение запросов 16,6 % / 49,6 % / 33,8 %, что соответствует весам 1 : 3 : 2.

## Профиль нагрузки

`users = 100`, `spawn-rate = 5`, `run-time = 3m`, headless.

- Это самый частый сценарий: так банковским приложением пользуются каждый день. Поэтому пользователей
  здесь больше, чем в сценариях выпуска карт.
- Стенд целиком работает на машине с 2 vCPU, генератор нагрузки — на ней же. Пробные прогоны по 2 минуты:
  - 100 пользователей — около 45 RPS, p95 ≈ 140 мс, CPU машины ≈ 165 % из 200 %;
  - 150 пользователей — RPS вырос только до 61 вместо ожидаемых ~70, p95 ≈ 710 мс, CPU машины ≈ 177 %.
    Это уже перегрузка, а не рабочий режим.

  В уроке для похожего gRPC-сценария было 300 пользователей. На этой машине при такой нагрузке медиана
  ответа вырастает до секунд, поэтому выбраны 100 пользователей.
- `spawn-rate = 5`: пользователи стартуют плавно, примерно за 20 секунд.
- Каждый виртуальный пользователь берёт случайного пользователя из 300 подготовленных, выбор идёт с повторами.
  По логам grpc-accounts в этом прогоне список счетов запрашивали 84 разных пользователя из сидинга,
  остальные 216 в тесте не участвовали.

## Сравнение с HTTP-версией

HTTP-версия сценария (`scenarios/http/gateway/existing_user_get_operations`) запускалась с 60 пользователями:
больше на этой машине HTTP не выдерживал. Веса задач те же.

| Показатель | HTTP, 60 пользователей | gRPC, 100 пользователей |
|---|---|---|
| Запросов / Fails | 4933 / 0 | 8399 / 0 |
| RPS | 27,4 | 46,7 |
| Aggregated p50 / p95 / p99, мс | 38 / 130 / 1100 | 24 / 93 / 220 |
| CPU шлюза | http-gateway ≈ 56 % | grpc-gateway ≈ 13 % |

gRPC выдерживает на 2/3 больше пользователей с меньшими задержками. Шлюз при этом тратит на один запрос
примерно в 7 раз меньше CPU.
