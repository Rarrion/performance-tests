# Выпуск виртуальной карты существующим пользователем

Сценарий (`TaskSet`): существующий пользователь получает список своих счетов и выпускает новую виртуальную карту.

Запуск из корня проекта:

```bash
locust --config=./scenarios/http/gateway/existing_user_issue_virtual_card/v1.0.conf
```

Хук `events.init` перед стартом нагрузки выполняет сидинг `ExistingUserIssueVirtualCardSeedsScenario`:
300 пользователей, у каждого дебетовый счёт. Сидинг занимает около 20 секунд, результат сохраняется
в `dumps/existing_user_issue_virtual_card_seeds.json`. `build()` при каждом запуске создаёт новых пользователей
и перезаписывает этот файл.
В `on_start` каждый виртуальный пользователь получает случайного пользователя из сидинга:
`get_random_user()` сохраняется в `self.seed_user`.

## Веса задач

| Задача | Вес | Почему |
|---|---|---|
| get_accounts | 3 | с него начинается работа с приложением; после выпуска карты пользователь обновляет список счетов, чтобы увидеть новую карту (карты приходят в ответе на список счетов) |
| issue_virtual_card | 1 | выпуск карты — редкое действие, поэтому у него минимальный вес |

В отчёте фактическое распределение запросов 74,7 % / 25,3 %, что соответствует весам 3 : 1.

## Профиль нагрузки

`users = 50`, `spawn-rate = 3`, `run-time = 3m`, headless.

- Флоу частый и критичный, но карты выпускают реже, чем смотрят операции. Поэтому пользователей
  здесь меньше, чем в самом частом сценарии получения операций (60), и больше, чем в сценарии
  нового пользователя (30).
- Стенд работает на машине с 2 vCPU. На пробных прогонах с 60 и 80 пользователями стенд упирался в CPU,
  и p95 вырастал до 1,2–1,3 с. При 50 пользователях после разгона p95 держится на 120–220 мс.
- При `spawn-rate = 3` пользователи стартуют плавно, примерно за 17 секунд.
- Каждый виртуальный пользователь берёт случайного пользователя из 300 подготовленных. Поэтому в тесте
  участвует не больше 50 разных пользователей из сидинга, остальные остаются в запасе.

## Результаты (report.html)

Прогон: 30.09.2026 22:30:08–22:33:08 UTC. В report.html время показывается в часовом поясе браузера, на скриншотах Grafana — в UTC.

| Запрос | Запросов | Fails | p50, мс | p95, мс | p99, мс |
|---|---|---|---|---|---|
| GET /api/v1/accounts | 3029 | 0 | 67 | 200 | 1100 |
| POST /api/v1/cards/issue-virtual-card | 1024 | 0 | 92 | 250 | 1000 |
| **Aggregated** | **4053** | **0** | 74 | 220 | 1100 |

- Fails = 0, RPS в среднем ≈ 22,5, после разгона ≈ 23–25.
- Хвост p99 около 1 с набирается только за первые 20 секунд, пока стартуют пользователи. В этот момент
  p95 в отчёте доходит до 1–1,5 с, после разгона держится на 120–220 мс. Причина та же, что и в сценарии
  получения операций: `GatewayHTTPTaskSet.on_start` создаёт 5 `httpx.Client`, каждый примерно за 60–80 мс CPU
  (создание SSL-контекста). При 3 новых пользователях в секунду это почти вся секунда процессорного времени,
  и на время разгона event loop Locust блокируется.
- Выпуск карты медленнее списка счетов (медиана 92 мс против 67 мс): это запись новой карты, а не чтение.
- В TaskSet задача выпуска карты с весом 1 повторяется, поэтому виртуальный пользователь выпускает карты
  многократно (реальный пользователь — одну). Это осознанное ограничение модели нагрузки. Карты приходят
  в ответе на список счетов, поэтому ответ `GET /api/v1/accounts` тяжелеет: в среднем 3,9 КБ против 0,7 КБ
  в сценарии получения операций. Отсюда рост сетевого трафика при постоянном RPS на скриншоте сети —
  в реальной эксплуатации такого роста не будет.
