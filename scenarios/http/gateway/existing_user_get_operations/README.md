# Получение операций существующим пользователем

Сценарий (`TaskSet`): существующий пользователь получает список счетов, список операций и статистику по операциям.

Запуск из корня проекта:

```bash
locust --config=./scenarios/http/gateway/existing_user_get_operations/v1.0.conf
```

Хук `events.init` перед стартом нагрузки выполняет сидинг `ExistingUserGetOperationsSeedsScenario`:
300 пользователей, у каждого кредитный счёт и 7 операций (5 покупок, пополнение, снятие наличных).
Сидинг занимает около 80 секунд, результат сохраняется в `dumps/existing_user_get_operations_seeds.json`.
`build()` при каждом запуске создаёт новых пользователей и перезаписывает этот файл.
В `on_start` каждый виртуальный пользователь получает случайного пользователя из сидинга:
`get_random_user()` сохраняется в `self.seed_user`.

## Веса задач

| Задача | Вес | Почему |
|---|---|---|
| get_accounts | 1 | список счетов открывают один раз при входе, чтобы проверить баланс |
| get_operations | 3 | историю операций обновляют чаще всего, чтобы убедиться, что платёж прошёл |
| get_operations_summary | 2 | статистику открывают реже, чем историю, но тоже неоднократно |

В отчёте фактическое распределение запросов 16,8 % / 49,9 % / 33,3 %, что соответствует весам 1 : 3 : 2.

## Профиль нагрузки

`users = 60`, `spawn-rate = 3`, `run-time = 3m`, headless.

- Это самый частый сценарий, поэтому пользователей вдвое больше, чем в сценарии нового пользователя (30).
- Стенд работает на машине с 2 vCPU. На пробных прогонах 60 пользователей держатся стабильно:
  около 29 RPS, p95 около 100 мс, CPU хоста около 100–115 % из 200 %. При 100 пользователях Locust упирается
  в CPU и выдаёт предупреждение, а задержки растут до секунд. В уроке для похожего сценария было 300
  пользователей, но на этой машине такая нагрузка перегрузила бы и стенд, и сам генератор нагрузки.
- При `spawn-rate = 3` пользователи стартуют плавно, примерно за 20 секунд.
- Каждый виртуальный пользователь берёт случайного пользователя из 300 подготовленных. Поэтому в тесте
  участвует не больше 60 разных пользователей из сидинга, остальные остаются в запасе.

## Результаты (report.html)

Прогон: 30.09.2026 22:16:55–22:19:55 UTC. В report.html время показывается в часовом поясе браузера, на скриншотах Grafana — в UTC.

| Запрос | Запросов | Fails | p50, мс | p95, мс | p99, мс |
|---|---|---|---|---|---|
| GET /api/v1/accounts | 827 | 0 | 64 | 160 | 1200 |
| GET /api/v1/operations | 2462 | 0 | 33 | 130 | 1100 |
| GET /api/v1/operations/operations-summary | 1644 | 0 | 33 | 110 | 1000 |
| **Aggregated** | **4933** | **0** | 38 | 130 | 1100 |

- Fails = 0, RPS в среднем ≈ 27,4, после разгона ≈ 29–30.
- Хвост p99 около 1 с набирается только за первые 20 секунд, пока стартуют пользователи. В этот момент
  p95 в отчёте доходит до 0,65–1,3 с, после разгона держится на 70–120 мс. Причина на стороне генератора
  нагрузки: `GatewayHTTPTaskSet.on_start` создаёт 5 `httpx.Client`, каждый примерно за 60 мс CPU
  (создание SSL-контекста). Пока пользователи стартуют, это блокирует event loop Locust.
  Сервисы в это время загружены слабо: CPU http-gateway около 20 %.
